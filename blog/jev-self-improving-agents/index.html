Whether an agent fixes code, answers support tickets, researches a question or drives a browser, it keeps arriving at the same kinds of fork. Is this result relevant? Is it enough, or should it keep looking? Which tool should run next? Did that step succeed, or should it try again? Does this need a human? Should it stop?

None of those are necessarily writing problems. They are decision problems. Yet we often hand them to a language model, ask it to generate a sentence or a JSON object, and then write code to interpret the result.

In September 2026, TypeSafe AI introduced Jev, its first System One Model, built for a different contract: unstructured state in, typed probabilistic decisions out. It doesn't need to write a paragraph to tell you which option it prefers. [1]

Deciding Without Generating Text: What Jev Is

A language model writes one token at a time. Each token needs its own forward pass over everything before it, so a 40-token answer is 40 passes in a row, each limited by how fast the model’s weights can be read from memory. Many calls inside an agent do not need that: routing a request, filtering chunks and picking a tool are all choices among a few fixed outcomes.

Do we really need to generate tokens to make a decision?

A decision model reads the input once, in a single parallel pass called the prefill, and returns a probability for each outcome: no decoding, nothing to parse, and the harness keeps the confidence. Alex L. Zhang calls this changing a model’s “shape”, its input and output interface.

Jev, from TypeSafe AI, takes a state, the context to judge, and one or more typed questions, and returns a probability for each possible answer. There are three question types:

Choice

Choose one of several options.

“Which tool should run next?”
Score

Evaluate against a defined rubric.

“How strong is this evidence?”
Noul

Estimate a yes/no probability.

“Is this passage relevant?”

Questions are meant to be small and independent, and TypeSafe says Jev answers them in parallel. [1]

What is known. TypeSafe describes a new architecture and a training method, Reinforcement Learning for Calibrated Decisions (RLCD), aimed at probabilities you can use as confidence, but has not published either, so this post treats Jev as an interface. A typed answer can still be wrong, so test calibration on your own data; the 70–500 ms latencies are TypeSafe’s own figures. [1]

Inside an agent the roles are strict: Jev only judges. The harness, ordinary code with thresholds and rules, reads the probabilities and decides what to do.

Open Alternatives to Jev

Jev is a hosted API, but the contract, a state and typed questions in and a probability per answer out, is not TypeSafe’s alone. Open models now offer it too:

They get there differently, an encoder, a one-step diffusion pass, a small vision-language model, but return the same shape, and open weights matter most when data cannot leave the building. Typed is still not correct: a recent preprint found a decision head can follow an option’s name rather than its rubric, so test before swapping. Any of them can fill the judge slot in section 03.

Recursive Language Model Based Jev for Long Context

Figure 2 is the general pattern; here it is inside one specific harness. A Recursive Language Model (RLM) lets a root model work over a context far too long to read at once: the context sits in a Python REPL as a variable, and the root writes code that slices it, sends the pieces to sub-calls, and combines what comes back. [2] On an aggregation benchmark like OOLONG, [3] where even frontier models score under 50% at 128K tokens, most of those sub-calls ask the same small question about one record at a time: which label fits this?

New to RLMs? The idea is laid out in full in Alex L. Zhang and Omar Khattab’s original blog post, and Prime Intellect’s “Recursive Language Models: the paradigm of 2026” shows them managing long-horizon tasks in practice.

That is a decision, not a writing task, which makes it the natural place for Jev. Jordan Natan Hochenbaum kept the root model and swapped its generative sub-calls for three judgment functions that return probabilities or scores instead of text: [4]

jev_classify
a probability for each label, for every item: which category is this record?
jev_yesno
P(yes) for every item: does this record match the question?
jev_locate
a score for every passage against a query: where in the context is the answer?

The same swap reads differently against the real architecture. In Figure 3, the root model never decodes much itself. It first narrows the context with cheap code: a keyword filter (regex) keeps only the chunks that mention the right terms, and a relevance ranking (BM25) keeps the ones that match the query best, and the time goes into the fan-out on what survives, where every sub-query is another full language-model call that writes its answer out token by token, and the root cannot answer until the last one returns. For sub-queries that are really decisions, Jev collapses that whole row into a few batched requests, each small enough to stay accurate.

What happens next, and what the figure cannot show.

  1. The root answers. With Jev, only the IDs and scores of the relevant pages come back; the root reads those pages in full and writes the answer. On the left, the root first has to read four written answers, two of them only saying “not relevant”.
  2. The wait is set by the slowest call. Both sides run their calls at the same time, but the root cannot answer until the last one returns. A sub-agent that writes a long answer holds everyone up; a Jev call has nothing to write, so it finishes in about the time it takes to read.
  3. Only decisions move to Jev. Sub-queries that ask “is this relevant?” or “which label fits?” go to Jev. Ones that need writing, such as summarising a section or pulling out a number, still go to a generative sub-call, which may recurse as before.
  4. Nothing is thrown away. Pages Jev scores low stay in the REPL variable, so the root can look again if the answer turns out to need them.
  5. Measured versus drawn. The roughly 6× speed-up is Hochenbaum’s measurement on OOLONG [3]; the pages, token bars and scores in the figure are illustrative. [4]

The speed comes from two places. Jev is prefill-only, so there is no answer to decode token by token, and a single request can carry hundreds of records while requests run concurrently. Neither protects the answer. Here is the swap on its own, at roughly one million tokens on OOLONG, [3] against a Haiku sub-call baseline: [4]

6× faster · half the cost · score 0.70 vs 0.75

Faster and cheaper, but not the same result. What carries the result across is what the probabilities make possible:

Ask per record, by ID

Up to a few hundred records can share a request, but only if each has its own question and a visible ID.

95–97% accurate at 250 per request; 26% when records had to be found by position.
Calibrate the labels

Fit one weight per label on a small labeled sample, in the request format you will actually run.

300 labeled items: count error 7.9% → 2.6%.
Gate the doubtful ones

Let confident judgments through and send only the least confident records to a generative model.

12% sent to Haiku: 91.5% on MultiNLI, above either model alone.

A generated label carries no confidence, so there is nothing to calibrate or gate on. The caveats are real, though: most of these runs used 20 questions or fewer, the gating result comes from MultiNLI rather than an RLM, and under load Jev throttled well below its documented 80 requests per second. [4] At scale, Ling and colleagues found the same limit: across 4,500 executions, Jev cut decision cost by 66–78%, yet task success fell for two agents. [5] Weitekamp’s Recursive Decision Models, which recurse with Jev alone, are promising but not yet benchmarked. Faster decisions are not a better agent; measure the result on your own task.

An RLM fixes long context in the harness. Zhang, who co-created RLMs and in the same essay calls Jev “quite useful” for RLM harnesses, points to where the fix could go next: into the model itself, as a shape that keeps “dense attention locally with an ‘auto-compacting’ history”, so an agent no longer needs a harness to compact its own past. That is a research direction, not yet a result.

Jev as Memory: Exhaustive Judgment with Abstention

The contribution in one sentence. Instead of letting a generative model choose which few memory blocks to open, split every block into chunks of N characters, score every chunk with a calibrated judge, and widen the look only where the judge cannot decide. This section is an architecture proposal with a cost model and testable predictions, not results; none of it has been run.

Why now. MemGPT and Manus let the agent decide what to retrieve, but every look is a generation, so they can only afford a few. Jev-Mem, a September 2026 preprint, puts Jev in control of memory traversal and reports 0.777 against 0.700 for the strongest baseline on LoCoMo, with memory built 6.6× faster. This proposal takes the simpler route Jev makes affordable:

Look at everything, cheaply, and spend generation only where the judge abstains.

In plain words. Think of an agent’s memory as a huge pile of notes: tool results, documents, chat messages, facts about the user. Today, an LLM reads a short index and picks a few notes to open, so anything it did not think to open is missed. The proposal flips that around:

  1. Cut every note into small, equal pieces, sorted by kind, small enough for Jev to read at once.
  2. Let the LLM write down, once, what to look for in each kind of note.
  3. Let Jev check every single piece: keep, drop, or unsure. It is fast and cheap because it reads but never writes.
  4. Give the LLM only the kept pieces to answer from. An unsure piece is checked again with the pieces around it, never thrown away on a guess.

Architecture

What happens next, and what the figure cannot show.

  1. The routing really runs, as code. We adopt executable code actions, the CodeAct approach: instead of describing its plan in text or JSON, the agent writes a few lines of Python, the route(…) calls in the figure, and an interpreter executes them. Each route sends one rephrased part to one kind of memory, and jev_filter hands every piece to Jev. Because it is real code, the plan can loop over parts or branch on what Jev returns without another LLM call, and if a line fails, the error comes back to the agent to fix. Wang et al. found this raised agents’ success rates by up to 20% over JSON or text actions across 17 LLMs. [6]
  2. The LLM answers. The pieces Jev lets in, plus the question, become the LLM’s context window, filled in order of Jev’s confidence until a token budget is reached. This is the second and last time the LLM writes.
  3. Unsure pieces get a wider look, not a guess. Jev first rereads an unsure piece together with the pieces beside it. Only if it is still unsure does the LLM read the whole note, the one expensive step, and only for the few pieces that need it.
  4. Nothing is thrown away. A left-out piece keeps its ID and a link back to its source, so the agent can fetch it later if the answer needs it.
  5. One call, many pieces. Jev judges a whole batch of pieces in a single request, and each piece costs one cheap read with no writing. N stays well under Jev’s 32k-token limit, and neighbouring pieces overlap a little so a sentence cut in half is still whole in one of them.
  6. The numbers are learned, not guessed. N, the confidence floor for “unsure” and the token budget are tuned on real outcomes, with the loop in section 04.

Why a Piece Goes In or Stays Out

Two words first, since the figure uses both:

Tool call
the record of one action the agent took: the tool’s name, what it was asked, and what came back, such as P/E ratio → 32x. Usually short, so it stays one piece.
Chunk
one N-character piece of a longer block, such as part 2 of 3 of an earnings report. A long document becomes several chunks, and each is judged on its own.

Jev does not look for the word “NVIDIA”. It reads each piece together with its lane’s question and asks one thing: does this help answer it? That is a judgment about meaning, so it can go against the words. Earnings 2/3 never says “growth”, only that data-center sales rose 40%, and still scores 0.94 against “I need growth and margins”. The analyst report names NVIDIA in its first line, but it covers another sector, so it scores 0.12 and stays out.

Regex and BM25 match words. An LLM understands, but writes. Jev understands, and only reads.

The LLM row is the familiar baseline. A normal agent without Jev asks its model about each piece and gets a sentence back. Every token of that sentence is its own forward pass, so 16 pieces of about 25 written tokens each is roughly 400 passes in a row before the agent can even start its answer, and the result is text that still has to be parsed, with the model’s confidence thrown away. Jev reaches the same verdicts the way the LLM does, by understanding the piece, but pays only for reading it.

Memory store, segmented at write time. As memory is built, it is cut into typed blocks: tool calls, documents, conversation turns, and a user profile: stored facts about the user, such as their risk level and portfolio limits. Each block is then split into chunks of N characters, with a small overlap so a fact cut at a boundary is still whole in one of them. N exists because the judge has a window: Jev takes at most 32k tokens of state plus its longest question, 64k with every question, and an agent’s memory outgrows that within hours. Keeping N well under the limit also keeps each judgment small. Every chunk carries its block’s header and a restorable handle, a file path, URL or message ID, so dropping it from context can be undone; this follows Manus’s rule that compression must be restorable. Nothing is truncated and nothing is deleted.

Query expansion, written as code. One generative call turns the question into asks for each segment: which tool to run, what to search for, what the user already said. Following CodeAct, which found that letting agents act in executable Python rather than JSON or text raised success rates by up to 20% across 17 LLMs, [6] the expansion is a small program, a few route(…) calls ending in a call to the judge, so it can loop, branch and reuse the asks without another generation. A question like this is really a bundle of needs: what we own, why we bought it, what the numbers say now, and what our limits allow. So the agent writes each one as a plain need, “I need our NVIDIA shares” and “I need the forward P/E” for the tools, “I need growth and margins” for the documents, “I need why we bought it” for past conversations, and “I need our limits” for the user profile. The agent decides what to look for; Jev decides which stored pieces and which tools meet each need, by comparing the need with each tool’s definition as it is set in the backend. It is the only generation before the answer, and it is cached per query.

Judge. For each chunk, the state is the chunk itself, N characters plus its block’s header, and the questions are the k asks for its segment, each asked as a Choice: relevant, irrelevant, can’t tell. Jev takes all k questions in one request, and TypeSafe says independent questions are evaluated in parallel, [1] so a chunk costs roughly one prefill. A chunk’s score is its highest relevance probability across the asks.

Abstention cascade. This is the part earlier systems do not have.

“Can’t tell” is a real answer, not a low-confidence fallback. A chunk that cuts a fact in half, or needs the sentence before it, should produce it, and the chunk then gets a wider look instead of a guess.

Budgeted expansion. Relevant chunks are expanded into the working context in descending probability until a token budget T is reached. The rest stay out as IDs with their handles, so the model can still ask for them.

Cost Model

Let C be the number of chunks, about the memory size divided by N; N the chunk length in tokens; k the asks per segment; q the tokens per ask; G the cost of one generative read; and a1, a2 the abstention rates at tiers 1 and 2.

  • Tier 1: C · (N + k·q) prefill tokens, one pass over the whole memory
  • Tier 2: a₁ · C · (3N + k·q) prefill tokens, a chunk with one neighbour each side
  • Tier 3: a₁ · a₂ · C · G

Selective expansion in the MemGPT style, with m decision rounds that each read an index of B block summaries of length s and generate a decision costing D to decode, costs m · (B·s + D).

Tier 1 reads the entire memory once, so unlike a search it grows with memory size; what makes it affordable is that it is prefill only, with no decoding per chunk. Inside it, N is a trade-off: larger chunks spread the k·q question overhead over more text, smaller chunks keep each judgment focused. Exhaustive judgment wins when prefill is cheap relative to decode and a1 is small; at a1 ≈ 1 tier 2 roughly triples the cost. Plug in your own provider’s prefill and decode prices to find the crossover for your workload.

Interfaces

Chunk header, carried by every chunk: block_id · chunk_index · type · source · timestamp · handle.

Judge. Anything that returns calibrated probabilities over typed options can fill the slot: Jev today, an open typed-decision model, or a fine-tuned classifier with a confidence head. The architecture is not specific to Jev; Jev is the first model that makes it cheap, and section 01 lists the open alternatives.

Questions. A Choice over relevant, irrelevant, can’t tell for the gate, and optionally a Score in [0, 1] for usefulness, to rank within the relevant set.

Budget rule. Expand by probability until T, and log every expansion with its tier and probability. That log is the hook for the learning loop in section 04; the learning itself is out of scope here.

Predictions and Risks

What I expect, written so it can be shown wrong:

  1. Judgment quality peaks at some chunk length N*: shorter chunks lose the context that makes them relevant, longer ones mix relevant and irrelevant text in one verdict. N* is smaller for message blocks than for tool blocks, whose outputs are long and front-loaded with boilerplate.
  2. The tier-1 abstention rate falls steadily as N grows. If it does not, the judge is answering from the option names, not the content.
  3. Renaming the options to A / B / C, with the rubric in the instruction, shifts results more than changing N does: the option-name sensitivity reported for constrained decision heads applies here.

And the risks I already know about:

  • Chunk boundaries are the whole game. Fixed N-character cuts are the baseline; cutting on sentence, turn or field boundaries, with a small overlap, is the obvious upgrade and the first thing to try.
  • Relevance that needs two blocks together. Judging block by block cannot see that block 7 matters only because of block 12. Multi-hop questions are the expected failure case.
  • Option-name following. If the judge keys on the word “relevant” rather than the rubric, abstention becomes noise. Prediction 3 is the check.

From Judgment to Learning: Jev as a Harness Controller and a Training Signal

A retry is not learning. An agent that reruns a failing test or re-queries a tool is correcting its current run, and next time it may make the same mistake. Learning means changing a reusable policy, and only after the outcome has been checked by something other than Jev. Jev does not learn from every interaction, and nothing in this design does by default: an agent improves only when the surrounding system updates its policy using verified feedback. Figure 5 follows one full turn.

Credit Assessment: Did the Piece Actually Help?

Step 4 is the one most loops skip. Jev’s score is a prediction, made before the answer exists. Credit is a measurement, made after the answer has been verified: did including the piece change whether it was right?

Relevance is a prediction. Credit is a measurement.

How to measure it. Start with leave-one-out: rerun the answer without each kept piece and check it again. It costs one extra answer per piece and is exact when pieces act independently. When two pieces carry the same fact, or only help together, leave-one-out misreads both; a sampled Shapley value fixes that by averaging a piece’s effect over random subsets of the others, as in Ghorbani and Zou’s Data Shapley, at the cost of many reruns. ContextCite is a cheaper middle ground; attention scores show where a model looked, not whether a piece changed the answer.

What Has Been Shown, and What Has Not

Jev’s own weights stay frozen; what learns is the harness around it, or a separate model. In the harness, DSPy’s ReAnchor re-fits Jev’s thresholds, cuts and weights from labeled examples. In an email-triage test it cut missed replies from 48 to 5, at the cost of 47 more false alarms, and a three-level classifier went from 239 to 294 correct out of 336. [7] Hochenbaum’s per-label weights are the same move inside an RLM. [4] In training, Ma and colleagues used a frozen Jev to guide a separate reinforcement-learning agent, which beat a standard learner across nine MiniGrid tasks and three Atari games. [8]

Jev’s judgment can steer learning. It cannot be what learning is graded against.

Train on Jev’s ratings as if they were ground truth and the agent learns Jev’s mistakes: Gao, Schulman and Hilton showed that pushing too hard against a learned reward eventually lowers the true one. [9] The evidence is also narrow. ReAnchor traded false alarms for recall rather than improving both, Ma et al.’s results are in games, and the full loop in Figure 5 is my proposal, not a measurement.

How to tell it is learning. Log every decision with its probability, the policy version that acted on it and the verified outcome, then compare versions on a locked holdout: calibration, so that 0.9 means right about 90% of the time (Guo et al.); the gate’s risk–coverage curve (selective classification); labels spent per point of gain (Lewis and Gale); and, above all, end-to-end task success. [5] Moving a threshold only slides along the risk–coverage curve, trading recall for false alarms, as ReAnchor did; real learning lifts the curve.

A loop that learns lifts the curve. A loop that only loops slides along it.
