Whether an agent fixes code, answers support tickets, researches a question or drives a browser, it keeps arriving at the same kinds of fork. Is this result relevant? Is it enough, or should it keep looking? Which tool should run next? Did that step succeed, or should it try again? Does this need a human? Should it stop?

None of those are necessarily writing problems. They are decision problems. Yet we often hand them to a language model, ask it to generate a sentence or a JSON object, and then write code to interpret the result.

In September 2026, TypeSafe AI introduced Jev, its first System One Model, built for a different contract: unstructured state in, typed probabilistic decisions out. It doesn't need to write a paragraph to tell you which option it prefers. [1]

Do We Really Need to Generate Text to Make a Decision?

Large language models are built for autoregressive generation: every output token costs a full forward pass conditioned on everything before it, so latency and cost grow with the length of the answer, and the decoding loop is bound by memory bandwidth rather than compute. That interface is extraordinarily flexible, but many calls inside an agent do not need it. Routing a request, filtering retrieved chunks, picking the next tool: each is a choice over a small, fixed set of outcomes.

Do we really need to generate tokens to make a decision?

The goal is to keep the model's language understanding while dropping the generation a decision does not need. A decision model runs the input through a single forward pass, the prefill, and returns a probability for each predefined outcome: no decoding loop, no parsing. Several judgments about the same input (which route, which tool, which chunks are relevant) can share that one pass, and the harness keeps the full distribution, so it can act on confidence instead of a single label.

That gap is the key idea behind Jev. It is not a chatbot that has learned to answer briefly: a short generated answer still pays one decoding step per token, and still loses its confidence when the harness parses it.

What changes is the shape of the output.

Instead of a token sequence, Jev returns a probability over a typed set of answers, read off a single pass over the input. Alex L. Zhang makes the general case in his essay on language model “shape”: changing a model's input and output interface is what unlocks different cost and latency trade-offs for agent harnesses.

Where the idea came from. In TypeSafe's launch essay, founder Diogo Almeida argued that machine intelligence also needs an interface software can depend on. He describes a new stack behind Jev: a new model architecture, a parallel sampler, and a training method called Reinforcement Learning for Calibrated Decisions (RLCD). These are TypeSafe's claims, not a published recipe for reproducing the underlying architecture. [1] The name echoes Daniel Kahneman's distinction between fast, intuitive System 1 judgments and slow, deliberate System 2 reasoning.

So, What Is Jev?

Jev is a decision-oriented model built by TypeSafe AI. Its interface has two ingredients:

State
the context or information to evaluate
Typed questions
one or more judgments the application wants

Jev returns answers in a predictable structure, including probabilities that the surrounding software can act on. [1]

TypeSafe exposes three main question primitives:

Choice

Choose one of several options.

“Which tool should run next?”
Score

Evaluate against a defined rubric.

“How strong is this evidence?”
Noul

Estimate a yes/no probability.

“Is this passage relevant?”

These questions are meant to be small and independent. Rather than requesting a long chain of reasoning inside one question, an application can break a complicated task into separate judgments and combine them in code. TypeSafe says Jev evaluates independent questions in parallel. [1]

The point is not to replace all reasoning with a yes/no button. It's to avoid paying for elaborate reasoning when a well-scoped judgment will do.

One necessary distinction: a typed answer can still be wrong. The interface protects the output format; factual accuracy and confidence calibration must be tested for each use case. TypeSafe reports end-to-end response times of 70–500 ms, measured on workflows its own team built, and itself expects those numbers to be on the higher end of real-world gains. [1]

So how does Jev fit into an agent? The pattern is the same for almost any agent. The agent keeps doing what it already does: retrieving evidence, calling tools, drafting answers. When it reaches a fork, such as whether its evidence is enough or which tool to run next, it does not write a large second prompt. It sends Jev the current state and a few specific questions, and lets the harness decide what happens next.

Here's a simplified simulation of what a Noul question could do. Switch between three evidence states and watch a harness decide whether to answer or retrieve more. The probabilities below are illustrative examples, not live Jev responses.

Notice something important: Jev did not rewrite the document, plan a research project, or train itself. It answered a narrow decision question. The harness decided what to do with that judgment. That's precisely why the separation is interesting.

Recursive Language Model Based Jev

Figure 2 is the general pattern; here it is inside one specific harness. A Recursive Language Model (RLM) lets a root model work over a context far too long to read at once: the context sits in a Python REPL as a variable, and the root writes code that slices it, sends the pieces to sub-calls, and combines what comes back. [2] On an aggregation benchmark like OOLONG, most of those sub-calls ask the same small question about one record at a time: which label fits this?

New to RLMs? The idea is laid out in full in Alex L. Zhang and Omar Khattab’s original blog post.

That is a decision, not a writing task, which makes it the natural place for Jev. Jordan Natan Hochenbaum kept the root model and swapped its generative sub-calls for three judgment functions that return probabilities or scores instead of text: [3]

jev_classify
a probability for each label, for every item: which category is this record?
jev_yesno
P(yes) for every item: does this record match the question?
jev_locate
a score for every passage against a query: where in the context is the answer?

The same swap reads differently against the real architecture. In Figure 3, the root model never decodes much itself. It first narrows the context with cheap code: a keyword filter (regex) keeps only the chunks that mention the right terms, and a relevance ranking (BM25) keeps the ones that match the query best, and the time goes into the fan-out on what survives, where every sub-query is another full language-model call that writes its answer out token by token, and the root cannot answer until the last one returns. For sub-queries that are really decisions, Jev collapses that whole row into a few batched requests, each small enough to stay accurate.

The speed comes from two places. Jev is prefill-only, so there is no answer to decode token by token, and a single request can carry hundreds of records while requests run concurrently. Neither protects the answer. Here is the swap on its own, at roughly one million tokens on OOLONG, against a Haiku sub-call baseline: [3]

6× faster · half the cost · score 0.70 vs 0.75

Faster and cheaper, but not the same result. What carries the result across is what the probabilities make possible:

Ask per record, by ID

Up to a few hundred records can share a request, but only if each has its own question and a visible ID.

95–97% accurate at 250 per request; 26% when records had to be found by position.
Calibrate the labels

Fit one weight per label on a small labeled sample, in the request format you will actually run.

300 labeled items: count error 7.9% → 2.6%.
Gate the doubtful ones

Let confident judgments through and send only the least confident records to a generative model.

12% sent to Haiku: 91.5% on MultiNLI, above either model alone.

A generated label carries no confidence, so there is nothing to calibrate or gate on. The caveats are real, though: most of these runs used 20 questions or fewer, the gating result comes from MultiNLI rather than an RLM, and under load Jev throttled well below its documented 80 requests per second. [3] At scale, Ling and colleagues found the same limit: across 4,500 executions, Jev cut decision cost by 66–78%, yet task success fell for two agents. [4] Weitekamp’s Recursive Decision Models, which recurse with Jev alone, are promising but not yet benchmarked. Faster decisions are not a better agent; measure the result on your own task.

How Jev Helps Agents Improve: In the Harness and in Training

There's a small but crucial trap in the phrase self-improving agent. An agent that says “let me try that again”, whether it is rerunning a failing test, re-querying a tool or re-clicking a button, is not necessarily learning anything. It may be merely correcting its current run. Next time, it might make exactly the same mistake.

There are two loops. The first repairs a single answer. The second changes a reusable policy after evaluating real outcomes. Jev can supply the judgments in either loop; the harness has to implement the feedback and updates.

Jev does not train itself, and nothing here needs it to. What it adds to a learning loop is a probability on every judgment, and that number is what makes improvement measurable: you can see how confident each decision was, check it against what actually happened, and adjust. There are two places to put that to work. In the harness, the rules that act on Jev's output change. In training, a different model's weights change. In both, Jev's own weights stay frozen.

In the harness. This is the cheapest kind of improvement, and the best evidenced. Log every decision with its probabilities and the policy version that acted on it, get an independent outcome for it, and re-fit the numbers the harness uses. DSPy's ReAnchor optimizer does exactly this for Jev, tuning thresholds for Noul, cuts for Score and weights for Choice from labeled examples. In an email-triage test it cut missed emails needing a reply from 48 to 5, at the cost of 47 more false alarms, and a three-level classifier went from 239 to 294 correct out of 336 held-out emails. [5] Hochenbaum's per-label weights, in the RLM section above, are the same move inside an RLM. [3] The new policy is saved as a version, tested on a locked holdout, and rolled back if it does worse.

The probabilities can also choose what to learn from. The gate in Figure 3 already sends the least confident judgments to a person or a stronger model, and each of those answers is a fresh label exactly where the policy is weakest. That is uncertainty sampling, a classic active-learning strategy: label the items the model is least sure about. Feeding them into the next re-fit closes the loop. For Jev, that last step is still my proposal rather than a published result: the gate [3] and the re-fit [5] have each been shown, but not yet wired together.

In training. Here Jev is a judge for something else that learns. Yi Ma and colleagues used a frozen Jev as a reference policy, an exploration judge and a replay rater while a separate reinforcement-learning agent trained. Across nine MiniGrid tasks and three Atari games, the Jev-guided methods outperformed a standard RL learner in their reported experiments. [6] The same role carries over to data. When I fine-tuned a model for Saudi filings, the training labels were bootstrapped from a commercial OCR pass and then filtered; a calibrated checker like MiniCPM-OCR Jev could do that filtering, keeping only the labels most likely to be right. [7]

Jev's judgment can steer learning. It cannot be what learning is graded against.

If an agent trains on Jev's ratings as if they were ground truth, it learns Jev's mistakes and grows more confident in them. Gao, Schulman and Hilton measured this directly: pushing optimization too far against a learned reward model eventually lowers the true reward, as the policy learns to exploit the proxy. [8] Every loop in Figure 5 is anchored on something independent: verified outcomes on the left, real reward or verified labels on the right. The evidence is also narrower than it looks. ReAnchor traded false alarms for recall rather than improving both; Ma et al.'s result is reinforcement learning in games, not proof that a RAG agent improves; and the gate-to-label loop and the data-filter role are proposals, not measurements.

Evidence quality matters. Blogs and vendor case studies can be useful engineering reports; preprints can be rigorous without yet being peer-reviewed. None of the studies above establishes that simply adding Jev to an arbitrary agent makes it self-improving. The strongest transferable evidence is for calibrating a policy from independent labels and using Jev to guide an independently trained learner.

OCR-Based Jev

The same contract is now showing up outside TypeSafe. OpenBMB's MiniCPM-OCR suite ships two models side by side: MiniCPM-OCR 1.0, a 1.3B parser that turns pages into text, and MiniCPM-OCR Jev, a 2B model that transcribes nothing at all. It looks at one region of a page (text, formula or table) together with the text an OCR model produced for it, and returns a single score between 0 and 1: how likely that output is to be correct. [7]

That is the System One idea from the start of this post, pointed at the step I care about most. In my work on Saudi financial filings, the worst failure was never an unreadable page; it was confident, well-formed, wrong figures. A checker that scores every region turns “trust the whole page” into “review these three cells” (Figure 6). OpenBMB does not say how the name relates to TypeSafe's model, but the shape is the same: context in, one probability out.

Three things in that table matter more than the ranking. Size: a 2B checker lands within 0.2 points of a 397B general-purpose model, which is too close to call without confidence intervals, at a small fraction of the parameters. Specialization: the 2B checker beats the 35B JEV model by 3.5 points; a narrow question rewarded a narrow model. Portability: scoring the output of four different parsers (MiniCPM-OCR 1.0, GLM-OCR, PaddleOCR-VL-1.6 and Xiaomi-OCR-0), it stays between 91.9 and 93.4, though on only 200 samples. [7]

So what changes is not that a decision model reads documents better than an OCR model does; it reads nothing. What changes is that verification becomes a cheap, separate step with a number attached, the same move as the confidence gate in Figure 3: send only the low-scoring regions to a person or a bigger model. The usual caveats hold. These are the authors' own numbers on their own benchmark, its size and composition are not described in the release, and OpenBMB itself advises setting the review threshold only after checking it on “a small batch from the real application”. [7]
